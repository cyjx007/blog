## 写在前面

我们习惯把“代码在 GitHub 上”当成一种保障。

但仓库是别人的。作者可以转私有，可以改名，也可以直接删掉。删掉之后：

- `git pull` 返回 404；
- 镜像仓库返回 403；
- 你本地如果没有 fork、没有镜像，就什么都不剩。

这篇记的就是一次这样的经历。好消息是最后救回来了；坏消息是，救回来纯属运气——因为那台机器上还跑着一个旧容器。

## 一、事情是这样的

那天想拉一下更新，终端里是一句很干脆的：

```
remote: Repository not found.
fatal: repository '...' not found
```

第一反应是“网络问题”或者“token 失效”。换浏览器打开，404。

再去镜像仓库拉运行中的镜像：

```
denied: requested access to the resource is denied
```

连匿名拉取 token 都拿不到。

到这一步可以确认：不是转私有，是**仓库和镜像包一起被删了**。

## 二、盘点：我到底有什么

冷静下来列了一张表：

| 东西 | 有没有 | 在哪 |
| --- | --- | --- |
| 正在运行的容器 | 有 | 一台常开的机器上 |
| 运行数据的每日备份 | 有 | 同一台机器的备份目录 + 加密包 |
| 配置文件 | 有 | 加密包 |
| 镜像 | **没有** | 只在镜像仓库里，已经 403 |
| 源码 | **没有** | 只在别人仓库里，已经 404 |
| fork | **没有** | 当时根本没 fork |

这张表很刺眼：**我备份了数据，但没备份“能跑起来的东西”**。

数据可以恢复，配置可以重写，但没有镜像和源码，服务本身就跑不起来。

## 三、为什么运行中的容器能救命

容器镜像有一个很好的性质：**它是分层的、自包含的**。

只要容器还在跑，镜像就还在本机的镜像存储里。可以把它完整导出：

```bash
docker save <image> -o service-image.tar
```

导出的 tar 里包含所有层。换一台机器：

```bash
docker load -i service-image.tar
docker images | grep <name>
```

镜像 tag 会原样回来。`docker compose up -d` 时，只要本地有同名镜像，就不会再去远端拉——即使远端永远 403。

更幸运的是，这个镜像里 `/app` 放的是**完整源码**，不是编译产物。也就是说，除了镜像，还能单独把源码捞出来：

```bash
docker run --rm <image> tar -C / -czf - app > service-src.tar.gz
```

（实际做法是从运行中的容器 `docker cp`，或者起一个临时容器挂载出来；关键是别改原容器。）

这样一来，两份东西就到手了：

- **镜像 tar**：能直接恢复运行；
- **源码 tar**：能读、能改、能重新构建。

## 四、补做的备份

### 1. 两份产物，各留一份校验

```bash
sha256sum service-image.tar service-src.tar.gz
```

镜像大一些（几十 MB），源码只有几 MB。两个文件都保留原始 tag 和构建日期，方便以后判断版本。

### 2. 两个位置

- 常开机器上的备份目录；
- 笔记本上的离线副本。

只放一处不算备份。尤其是那台常开机器只有一块 eMMC，本身也是单点。

### 3. 私有归档仓库

源码单独建了一个**私有**归档仓库，推到 GitHub 和家里的 Forgejo 两处。

归档时做了三件事：

- **排除运行数据**：配置、缓存、业务数据都不进仓库；
- **去掉设备名和绝对路径**：README 里只写通用启动方式；
- **保留许可证和第三方依赖说明**：以后要重新构建时用得上。

Forgejo 那边开了「push 到不存在的仓库时自动创建」，并默认私有。这样以后归档新项目，不用先去网页上点一遍。

### 4. 恢复路径要写下来

备份最怕“有文件，但不知道怎么用”。所以恢复步骤也写进了 README：

```bash
docker load -i service-image.tar
docker compose up -d
```

如果要从源码重建，则是另一条路：看 `Dockerfile`，或者直接按入口命令跑。

## 五、几条教训

### 1. 容器不是备份

容器能跑，不代表你拥有它。镜像可能被清理，宿主机可能坏，`docker system prune` 也可能手滑。

**能跑 + 能重建 + 有离线副本**，才算备份。

### 2. 镜像仓库不是归档

镜像仓库是分发渠道，不是存储。上游删包、改 tag、覆盖 `latest`，你都控制不了。

真正要留的版本，应该 `docker save` 成文件，自己管。

### 3. fork 不等于备份

fork 只是多了一个副本，但：

- 如果没 fork，就什么都没有；
- fork 了也可能忘记同步；
- fork 的仓库仍然在别人的平台上。

更稳的做法是：**定期导出 + 私有归档 + 两个物理位置**。

### 4. 上游消失是正常事件

不要把“作者会一直维护”当成前提。个人项目、实验项目、公司内部项目，都可能某天突然消失。

对自部署的服务，至少问自己三个问题：

- 如果明天仓库 404，我还能把它跑起来吗？
- 如果镜像仓库 403，我本地有镜像吗？
- 如果这台机器坏了，另一个位置有副本吗？

### 5. 恢复要演练

“我有备份”和“我能恢复”是两件事。

最简单的演练：在一台干净机器上 `docker load`，看能不能起来；或者至少确认 tar 能解开、镜像 tag 对得上。

## 六、现在的状态

这个服务现在从本地镜像启动，compose 不再依赖远端。源码在私有归档里，运行数据每天备份，加密包在另一个位置。

它不是“永远不会挂”，但至少**上游再消失一次，我不会再从零开始找**。

## 最后

我们花很多时间选工具、配服务，却很少花时间想“如果它明天消失怎么办”。

这次运气好：容器还在跑，镜像里的源码还是完整的。下一次不一定。

所以，如果你也有一个“从别人仓库拉的、自己部署的服务”，不妨现在就做三件事：

1. `docker save` 一份镜像；
2. 把源码和启动方式归档到自己的私有仓库；
3. 在一台干净机器上试一次恢复。

花不了半小时，但能把“上游删库”从事故降级成麻烦。

## 写在前面

前几天把一份文档从聊天窗口粘到编辑器里，表格变成了一坨字——竖线变成了 Tab，代码围栏凭空消失，代码块里的 `# 注释` 被当成一级标题。

顺着这个坑把 Markdown 的规则重新捋了一遍，才发现真正的难点不是「不会写」，而是**「写了没生效」，而且它从不说你错了**。

这份手册按「你会用到的东西」排，不按规范顺序。每节都标了容易踩的地方，末尾有自检命令和速查表。想当查询手册用，直接跳到第 17 节。


Markdown 的设计目标是「**用纯文本写出能读的原稿，再交给程序转成 HTML**」。所以它的规则有两层：

- **语法**：哪些字符有特殊含义；
- **解析规则**：这些字符在什么情况下才算「生效」。

绝大多数人卡住，不是因为语法不知道，而是因为**第二层**——同样的写法，前面少个空行、缩进差一格、围栏丢了，就**不报错但结果不对**。

## 0. 先搞清楚：Markdown 有好几种「方言」

Markdown 最初是 2004 年 John Gruber 写的一份规范，但**它本身写得不够严谨**，各家实现各有各的解释。现在就三派：

| 名称 | 是什么 | 谁在用 |
| --- | --- | --- |
| **CommonMark** | 2014 年一群人把规则写成可测试的严格规范 | 大多数现代解析器的基础 |
| **GFM**（GitHub Flavored Markdown） | CommonMark + 表格 + 删除线 + 任务列表 + 脚注 + 裸链接自动识别 | GitHub、Gitea、**Forgejo**、GitLab |
| 各家私货 | 上面没有的扩展 | Obsidian 的双链、Typora 的数学公式、Hugo 的 shortcode |

**实用结论**：

- 想「在哪都能显示对」→ 只用 CommonMark 的核心部分（标题、强调、代码、列表、引用、链接）。
- 表格、删除线、任务列表这些是 **GFM 扩展**，CommonMark 里没有。微信、QQ、邮件正文基本都不支持。
- 具体某个地方支不支持，下面第 15 节有对照表。

## 1. 标题

```markdown
# 一级标题
## 二级标题
### 三级标题
#### 四级标题
##### 五级标题
###### 六级标题
```

只有 6 级，没有 `#######`。

**坑：`#` 后面必须有空格。**

```markdown
#这是标题      ← 不是标题，就是一行文字
# 这是标题     ← 对
```

还有种老式写法（Setext），用下划线：

```markdown
一级标题
========

二级标题
--------
```

**这个写法要小心**：你在文字下面随手画一条 `---` 想当分隔线，结果**上一行文字变成了二级标题**，而分隔线没了。所以分隔线前后一定留空行（见第 9 节）。

**实用建议**：

- 一篇文章只用 `#` 做标题一次（大标题），章节用 `##`，子节用 `###`。跳级（`##` 直接到 `####`）不会报错，但目录/大纲会乱。
- 标题里别放图片、别放换行。

## 2. 段落和换行（最容易出错的一节）

### 段落 = 至少一个空行分隔

```markdown
这是第一段。
它有两行，但属于同一个段落。

这是第二段。
```

在源码里换行，**不等于**在页面上换行。上面的「这是第一段。它有两行」会被渲染成**一行连续的文字**，中间只有一个空格。

想分段，中间必须**留一个空行**（两个换行）。

### 想在段落内强制换行

三种办法：

| 写法 | 说明 | 可靠性 |
| --- | --- | --- |
| 行尾加**两个空格** | CommonMark 标准做法 | ⚠️ 很多编辑器保存时会自动删行尾空格，然后失效 |
| 行尾加 `\` | CommonMark 也支持 | ✅ 推荐，不会被自动清理吃掉 |
| 行尾加 `<br>` | HTML，GFM 和 Hugo 都认 | ✅ 可靠，但源码看着不干净 |

```markdown
第一行\
第二行          ← 用反斜杠，最稳

第三行<br>
第四行
```

**这是真会踩的坑**：你在 VS Code / Zed 里用「行尾两空格」做换行，编辑器一开「保存时删除行尾空格」，全部失效——而且**它不报错**，你只会觉得「有时候行、有时候不行」。

### 什么时候「一个换行」就够了

**GitHub / Gitea 的评论框和 issue 里**，普通换行会直接渲染成换行（它们把软换行当硬换行处理）。但在 **Hugo 博客、README 文件**里，普通换行不会换行。

同一个 `.md`，在不同地方显示不一样，就是这个原因。

## 3. 强调：加粗、斜体、删除线

```markdown
*斜体*    _斜体_
**加粗**  __加粗__
***加粗斜体***
~~删除线~~
```

**坑一：星号和下划线的「空格规则」**

强调符号必须**紧贴文字**。下面这两种都**不会**生效：

```markdown
* 这不是斜体 *
_ 这也不是斜体 _
```

因为 `*` 左边是空格（或行首）、右边也是空格，解析器认为它就是个星号。

**坑二：下划线在单词内部不生效**

```markdown
snake_case_name     ← `_` 在单词中间，不会被当成斜体
```

这是故意设计的（否则写变量名会天天出事）。要强调就用 `*`。

**坑三：中文紧贴时**

```markdown
**加粗**中文          ← 正常，能生效
中文**加粗**          ← 正常
中文 **加粗** 中文    ← 正常
```

中文本身不是问题，问题只在**空格的位置**。规则是：左边如果是空白、右边如果是空白，就不算强调。

**实用建议**：全篇统一用 `*` 和 `**`，别混用 `_`，省得哪天写变量名出意外。

## 4. 代码

### 行内代码：一个反引号

```markdown
用 `git status` 看状态
```

**内容里有反引号怎么办？** 用双反引号包，并且首尾各留一个空格：

```markdown
`` 这里有 ` 符号 ``
```

### 代码块：三个反引号（围栏）

````markdown
```bash
git add -A
git commit -m "xxx"
```
````

**一定要写语言名**（`bash`、`nix`、`python`、`json`…）。理由：

1. 有语法高亮，读起来快；
2. 高亮插件会按语言做词法分析，`#` 开头不会被误判成标题；
3. 复制出来的人知道这是什么。

**围栏的坑**：

- 开始和结束必须**数量一致或结束更多**。用 3 个开始就得用 3 个以上结束。
- **围栏丢了，里面的内容会被当成正文解析。** 这是最惨的一种：代码里的 `# 注释` 会变成标题，`*` 会变成斜体，`- ` 会变成列表。**不报错，只是排版全乱。**
- 代码块内部**不解析任何 Markdown**，所以里面的 `**` `#` 都是安全的（只要围栏在）。

### 老式写法：缩进 4 个空格

```markdown
    这四行缩进会被当成代码块
```

能用，但**不推荐**：一是没法标语言，二是和列表嵌套冲突（列表里缩进 4 格是继续列表项，不是代码块）。

### 代码块放进列表里

要缩进**列表内容起始列 + 4**，通常就是 8 个空格：

````markdown
- 第一步，先看状态：

  ```bash
  git status -sb
  ```

- 第二步……
````

围栏那一行缩进 2 格（对齐列表文字）也常常能work，但不同解析器表现不一致，**缩进 4 格最保险**。

## 5. 列表

### 无序列表

三种符号都行，**同一个列表里最好统一**：

```markdown
- 项目一
- 项目二
+ 项目三
* 项目四
```

### 有序列表

```markdown
1. 第一
2. 第二
3. 第三
```

**反直觉的点：数字写错不要紧。**

```markdown
1. 甲
1. 乙
1. 丙        ← 渲染出来还是 1. 2. 3.
```

解析器会自己数。但**起始数字会被尊重**：

```markdown
3. 从三开始
4. 四
```

渲染成 `3. 4.`。想从别的数字开始，就写那个数字。

**坑：`1.` 后面必须有空格。** `1.文字` 不是列表。

### 嵌套

```markdown
- 一级
  - 二级（缩进 2 格）
    - 三级（再缩进 2 格）
- 回到一级
```

**缩进差一格就会崩**。常见错误：

```markdown
- 一级
 - 二级（只缩进 1 格，有的解析器认，有的不认）
```

**规则**：子列表要缩进到**父项文字开始的列**。`- ` 占两列，所以子项缩进 2 格就对齐了。用 `-` 写的时候，2 格、3 格、4 格大多都能work，但**同一份文档里统一用 2 格**最省心。

### 列表项的续行

```markdown
- 这是一个很长很长的条目，
  这一行是它的续行，缩进两格对齐。
- 另一个条目
```

不缩进的话，第二行会被当成**新段落**，列表就断了。

### 紧凑 vs 松散

```markdown
- 项目一
- 项目二
```

```markdown
- 项目一

- 项目二
```

**中间加了空行**，渲染出来每项外面会多一层 `<p>`，行距变大（叫 loose list）。写文章时这个差别挺明显，按需选。

### 任务列表（GFM 扩展）

```markdown
- [ ] 没做
- [x] 做完了
- [ ] 也没做
```

**坑**：`[ ]` 后面必须有空格，`[x]` 里 `x` 小写最保险（大写 `X` 也认）。

Gitea / Forgejo 里还能点一下勾选，但**点完不会自动提交**，只是给你看。

## 6. 表格（GFM 扩展）

```markdown
| 名称 | 说明 | 价格 |
| --- | --- | ---: |
| 甲 | 第一个 | 10 |
| 乙 | 第二个 | 20 |
```

渲染：

| 名称 | 说明 | 价格 |
| --- | --- | ---: |
| 甲 | 第一个 | 10 |
| 乙 | 第二个 | 20 |

### 对齐

冒号在哪边就往哪边靠：

```markdown
| 左对齐 | 居中 | 右对齐 |
| :--- | :---: | ---: |
```

### 五条硬规则

1. **第二行（分隔行）不能少**，少了整张表就不成立，会退化成一行普通文字。
2. **单元格里不能换行。** 想换行只能用 `<br>`。
3. **单元格内容里的 `|` 必须转义成 `\|`**，否则会把单元格切断。
4. **表格前面要有空行**，否则可能和上一行粘连。
5. **列数不用对齐**（源码可以不整齐），但**每行的列数要一致**，多了少了都会错位。

### 这张表为什么会变一坨？

如果你从聊天窗口、网页、Word 里把表格复制到编辑器，经常变成这样：

```
名称	说明	价格
甲	第一个	10
```

竖线 `|` 变成了 **Tab**，行还在，但**表格语法没了**——渲染器只看到一堆用 Tab 分隔的普通文字，于是按段落处理，全挤在一起。

**判断方法**：

```bash
grep -o '|' 文件.md | wc -l     # 有表格就不该是 0
grep -cP '\t' 文件.md           # 表格不该有 Tab
```

### 表格里能放什么

| 想放 | 能不能 | 写法 |
| --- | --- | --- |
| 行内代码 | ✅ | `` `git status` `` |
| 链接 | ✅ | `[文字](url)` |
| 加粗 | ✅ | `**粗**` |
| 换行 | ⚠️ 只能用 `<br>` | `第一行<br>第二行` |
| 竖线 | ⚠️ 要转义 | `\|` |
| 多行代码块 | ❌ | 换别的表达方式 |
| 列表 | ❌ | 用 `<br>` + 符号凑 |

## 7. 引用

```markdown
> 这是一段引用。
> 可以有好几行。
```

渲染成左侧一条竖线的块。常用于：摘录、注意事项、警告。

### 嵌套

```markdown
> 外层
>
> > 内层
```

### 引用里放代码块

**每一行都要加 `> `**：

````markdown
> 命令如下：
>
> ```bash
> git push
> ```
````

漏了 `>` 就会跑到引用外面。

### 引用里放列表

```markdown
> 注意两点：
>
> - 第一点
> - 第二点
```

## 8. 链接和图片

### 基本

```markdown
[显示的文字](https://example.com)
[带标题](https://example.com "鼠标悬停时显示")
```

### 引用式链接（长 URL 的救星）

```markdown
见 [官方文档][docs] 和 [另一个][other]。

[docs]: https://example.com/very/long/url/that/you/dont/want/to/repeat
[other]: https://example.org
```

好处：正文干净，同一个地址在多处引用时只写一次。定义可以放在文末，不影响阅读。

### 自动链接

```markdown
<https://example.com>        ← 尖括号，CommonMark 支持
https://example.com          ← 裸 URL，GFM 自动识别
```

裸 URL 是 GFM 扩展，CommonMark 里不会自动变链接。

### 图片

```markdown
![图片说明](图片地址.png)
```

`!` 不能少，少了就是普通链接。

**`alt`（方括号里的说明）别省**：图片加载失败时它顶替显示，读屏软件也靠它。

### 图片当链接（点图跳转）

```markdown
[![图片说明](图片地址.png)](https://跳转地址)
```

外面套一层 `[ ]( )`。

### 本地图片的相对路径

```markdown
![截图](./images/shot.png)
![截图](../assets/shot.png)
```

规则：**相对于当前 `.md` 文件所在目录**。写错路径不会报错，只会显示一个破图。

### 坑：URL 里有空格或括号

```markdown
[文字](<https://example.com/有 空格>)     ← 用尖括号包起来
```

或者把空格编码成 `%20`。中文地址一般能直接写（会被自动编码），但保险起见别在文件名里放空格和括号。

## 9. 分隔线

```markdown
---
***
___
```

三个以上，**单独占一行，前后留空行**。

**坑：`---` 紧跟在文字下面是标题，不是分隔线。**

```markdown
这是文字
---
```

上面这段会把「这是文字」变成**二级标题**。所以分隔线一定要前后空行。

## 10. 转义

在特殊符号前面加 `\`，让它变回普通字符：

```markdown
\* 这不是斜体，是星号
\# 这不是标题
\[ 不是链接
\\ 一个反斜杠
```

能转义的是 **ASCII 标点**（`\` `` ` `` `*` `_` `{}` `[]` `()` `#` `+` `-` `.` `!` `|` `>` 等）。

**中文全角标点不需要转义**，它们本来就没有 Markdown 含义。

## 11. 折叠块和注释（扩展功能）

### 折叠块（HTML）

```html
<details>
<summary>点我展开</summary>

这里可以写 Markdown，但**前后必须留空行**。

</details>
```

**坑**：`<details>` 和里面的 Markdown 之间**必须有空行**，否则里面的内容不会被解析，会原样显示成文字。原因是 CommonMark 把 HTML 块当成「原样输出区」，空行才是分界线。

**注意**：很多平台会**过滤掉 HTML**（微信、邮件、部分博客默认配置）。Hugo 默认会剥掉裸 HTML，除非在配置里开 `markup.goldmark.renderer.unsafe = true`。

### 注释（不会显示出来）

```markdown
<!-- 这段是给我自己看的，渲染后看不到 -->
```

可以拿来存草稿、标记 TODO。注意注释里不能出现 `--`（HTML 注释的规则）。

---

## 12. 脚注（GFM 扩展）

```markdown
这句话有个脚注[^1]。

[^1]: 这是脚注的内容。
```

渲染后底部会出现一个小数字链接。适合放「不影响正文的补充说明」。

**限制**：脚注定义里的内容能换行，但缩进要对齐，复杂内容（代码块、表格）容易崩，**别在脚注里塞重货**。

## 13. 中文排版几条习惯

这些**不是** Markdown 的规矩，是「好看」的规矩。

1. **中英文之间加一个空格**：`用 git 推代码` → 视觉上更透气。
2. **数字和中文之间加空格**：`3 个文件`。
3. **标点用全角**：句号 `。`、逗号 `，`、括号 `（）`，除非括号里全是英文/代码。
4. **行内代码和中文之间也可以加空格**：`` 用 `git status` 看状态 ``。
5. **别用空格缩进段落**：开头 4 个空格会变成**代码块**（老式写法），中文段落缩进两格在 Markdown 里没有意义，反而可能触发缩进代码块。
6. **一行别写太长**：源码里适当换行（软换行），对 diff 友好；渲染出来还是一段。

---

## 14. 文件本身的两条规矩

1. **编码用 UTF-8，不要 BOM。** BOM 是文件开头三个看不见的字节，有些解析器会把它们当正文，导致第一行标题失效或出现乱码方块。
2. **换行符统一 LF。** Windows 的 CRLF 在大多数渲染器里没事，但在 Git diff、shell 脚本、某些解析器里会出问题。Git 可以设 `core.autocrlf`，或者仓库里放 `.gitattributes` 统一。

## 15. 平台差异对照

| 功能 | GitHub / Gitea / **Forgejo** | Hugo 博客 | Obsidian | 微信 / QQ / 邮件 |
| --- | --- | --- | --- | --- |
| 标题、加粗、列表 | ✅ | ✅ | ✅ | ❌（纯文本） |
| 表格 | ✅ | ✅ | ✅ | ❌ |
| 删除线 `~~` | ✅ | ✅ | ✅ | ❌ |
| 任务列表 `- [ ]` | ✅ | ✅ | ✅ | ❌ |
| 脚注 | ✅ | ✅ | ✅ | ❌ |
| 裸 URL 自动链接 | ✅ | ⚠️ 看配置 | ✅ | ❌ |
| 裸 HTML（`<details>`） | ⚠️ 会过滤一部分 | ⚠️ 默认剥掉，要开 `unsafe` | ✅ | ❌ |
| 单换行 = 换行 | ✅（评论/issue 里） | ❌（要空行或 `\`） | ⚠️ 看设置 | — |
| 数学公式 `$x$` | ✅ | ⚠️ 要开扩展 | ✅ | ❌ |

**经验**：写给「不知道会显示在哪」的地方（比如复制到微信），就只用标题、列表、加粗、行内代码这四样，其余都当成普通文字。

---

## 16. 复制粘贴会丢格式（我踩过）

**从渲染后的页面、聊天窗口、Word、PDF 里复制 Markdown，几乎一定会丢标记。**

典型损失：

| 丢什么 | 变成什么 | 后果 |
| --- | --- | --- |
| 表格的 `\|` | Tab 或空格 | 整张表退化成一坨字 |
| 代码围栏 ` ``` ` | 消失 | 代码里的 `#` 变标题、`*` 变斜体 |
| 空行 | 消失 | 段落全揉一起 |
| 缩进 | 变空格或消失 | 列表层级崩掉 |

### 三行命令自检

粘完立刻跑一遍，比肉眼可靠：

```bash
grep -c '^```' 文件.md          # 应该是偶数（0、2、4…）
grep -o '|' 文件.md | wc -l      # 有表格就不该是 0
grep -c '^$' 文件.md             # 空行不该是 0
grep -cP '\t' 文件.md            # 有表格就不该有 Tab
```

### 根本解法

**要 Markdown 就让工具直接写文件**，不要经过「渲染 → 复制 → 粘贴」这一趟。纯文本复制是安全的，渲染过的复制不是。

## 18. 一句话总结

**Markdown 的问题几乎都不是「不会写」，而是「写了但没生效」，而且它从不报错。**

所以写完，先看一眼**渲染结果**，再回头数三个东西：

1. 空行够不够（分段的唯一手段）；
2. 围栏在不在（代码块和正文的边界）；
3. 缩进对不对（列表层级的唯一手段）。

这三样对了，剩下的都是锦上添花。

## 写在前面

这两天新建了一个目录，想把一些自己的东西收进去，顺手写了几份笔记。

然后连着踩了五个坑。这五个坑有一个共同点，值得单独写一篇：

**程序从头到尾没说过一句「你错了」。**

- 表格粘过去，变成了一大坨挤在一起的文字；
- 代码块里的 `# 写笔记` 变成了一个巨大的标题；
- 我在 `.gitignore` 里写的规则——**一条都没生效**；
- 新仓库到底会不会继承我在别的仓库挂的自动备份钩子；
- 两台设备共用一个 SSH 连接，然后**静默地**连到了错的那台。

如果它们报错，我十秒钟就改完了。麻烦就麻烦在：它们都"成功"了。

这篇把这五个记下来，然后试着找出它们背后共同的形状。

## 一、Markdown：容错是它的优点，也是它的陷阱

### 1. 表格粘贴过去，变成一坨字

我把一张表从聊天窗口复制到编辑器，看起来是这样的：

```
现在的状态项 值仓库 tanghuang/mynotes, private: true（已用 API 确认）remote ssh://...（单一远端，没有 GitHub）网页 http://... .gitignore 已经按「宁可多忽略」的保守策略写好：...
```

原本我写的是：

```markdown
| 项 | 值 |
| --- | --- |
| 仓库 | tanghuang/mynotes |
| remote | ssh://... |
```

问题在于：**渲染过的页面、聊天窗口、Word、PDF，复制出来的都不是 Markdown。**

竖线 `|` 变成了 Tab，换行变成了空格，代码围栏直接消失。而 Markdown 的解析器对此毫无意见——它只看到一段用 Tab 分隔的普通文字，于是老老实实按段落排版，把整张表挤成一个自然段。

数一下就知道：

```bash
grep -o '|' 文件.md | wc -l     # 0：表格语法彻底没了
grep -c '^$' 文件.md            # 0：连一个空行都不剩
grep -cP '\t' 文件.md           # 5：表格的竖线变成了 Tab
```

### 2. 代码围栏丢了，`#` 就变成标题

更隐蔽的一个。同一份文件里，代码块是这样写的：

````markdown
```bash
cd ~/mynotes
# 写笔记……
git add -A && git commit -m "..." && git push
```
````

围栏（那三根反引号）在粘贴时丢了。于是渲染器看到的是：

```markdown
cd ~/mynotes
# 写笔记……
git add -A && ...
```

`#` 后面跟着空格——**这是一个标准的一级标题**。所以页面上出现了巨大的「写笔记……」三个字，前后两行代码被当成普通段落。

**Markdown 不会说「这个反引号没有配对」**，它只会把后面的所有内容当成普通文字继续解析。围栏一丢，里面的 `#`、`*`、`- `、`1.` 全部活了。

### 3. 用两个空格做换行，然后被编辑器吃掉

Markdown 里想在段落内部换行，标准做法是**行尾敲两个空格**。

```markdown
第一行··
第二行
```

（`·` 代表一个空格）

这是规范里的写法，能用。但它有一个致命缺点：**很多编辑器保存时会自动删掉行尾空格**（VS Code 的 `files.trimTrailingWhitespace`、Prettier、各种 format-on-save）。

结果就是：**同一份文件，有时候换行生效，有时候不生效**，你查半天找不到原因——因为那两格空格在保存的那一瞬间已经消失了，你打开文件看见的是「我已经写了两个空格啊」。

三个办法，可靠性差很多：

| 写法 | 可靠性 |
| --- | --- |
| 行尾两个空格 | ⚠️ 会被编辑器、formatter 吃掉 |
| 行尾加 `\` | ✅ 推荐 |
| 直接写 `<br>` | ✅ 最不会出意外，但源码不好看 |

我现在一律用 `\`。

### 4. 顺便一个：`---` 到底是分隔线还是标题

```markdown
这是文字
---
```

你想画一条分隔线，结果**上一行变成了二级标题**，线也没了。

因为 Markdown 有一门老式标题语法（Setext）：文字下面跟一行 `---` 就是二级标题。

分隔线要成立，必须**前后都是空行**。

## 二、Git：沉默得更彻底

### 5. 我写的 `.gitignore` 规则，一条都没生效

这条最气人，因为它**完全没有反馈**。

我当时是这么写的：

```gitignore
*.kdbx   # 密码库
*.key    # 密钥
.env     # 环境变量
```

看着很合理吧？带注释，一目了然。

**全错了。**

gitignore 的 `#` **只能单独占一行**。写在规则后面的部分不是注释，而是**模式的一部分**——上面第一行被解析成「忽略文件名匹配 `*.kdbx   # 密码库` 的文件」，这个文件永远不存在。

它不报错，不警告，`git status` 也不提。你会以为密码库已经被保护了，然后某天 `git add -A` 把它一起推了上去。

正确写法：

```gitignore
# 密码库
*.kdbx
# 密钥
*.key
```

验证一遍，比肉眼可靠：

```bash
git status --ignored --short     # 到底忽略了什么
```

同一个文件里还有两个同类的坑：

- `!` 的优先级**不是**「后写的赢」，而是「**最后一个匹配的规则赢**」。想放行一个文件，反向规则必须写在后面。
- `.gitignore` 只对**未跟踪**的文件生效。已经提交过的文件，加规则也没用，得 `git rm --cached` 先摘出来。

### 6. 新仓库会不会跑别人的钩子

我机器上有个钩子：`push` 的时候在后台把登录态加密备份到家里的服务器，挂在两个仓库上。

新建一个仓库，我会不会被它"顺手带走"？

**不会**——但理由值得说清楚，因为它和大多数人的直觉相反：

```bash
~/code$          git config core.hooksPath    # → .dsh/githooks
~/nixos-config$  git config core.hooksPath    # → /home/<我>/code/.dsh/githooks
~/mynotes$       git config core.hooksPath    # → 空
```

**`core.hooksPath` 是仓库级配置。** 不写 `--global`，它就只对当前这个 `.git/` 生效。新仓库的 `hooks/` 里只有一堆 `*.sample`，一个都没启用。

这类「配置到底是全局的还是仓库的」问题，Git 里到处都是（`user.email`、`core.autocrlf`、`commit.template`……）。有个命令能一次问清楚：

```bash
git config --list --show-origin | grep 你想查的
# file:/home/<我>/.config/git/config   user.email=...
```

**先搞清楚哪个文件在生效，比瞎改快得多。**

### 7. 标签不会跟着 push 走

发版打了标签：

```bash
git tag -a v1.0.0 -m "首个版本"
git push
```

```
To github.com:xxx/yyy.git
   abc1234..def5678  main -> main
```

推送成功，输出干净。但**标签没上去**。别人 `git clone` 下来，找不到 `v1.0.0`。

要单独推：

```bash
git push --tags          # 全部标签
git push --follow-tags   # 推提交 + 与之相关的附注标签
```

## 三、SSH：静默失败里最危险的一种

这两个坑不是 Markdown、也不是 Git，但属于同一类，而且后果最严重。

### 8. 同一个地址，两台设备：会报错的那个

家里两台路由器（一台随身 Wi-Fi、一台备用），内网地址都是 `192.168.x.x`，**主机公钥不同**。

SSH 第一次连会记住对方的公钥，下一次公钥变了就拒绝——防中间人，设计合理。

所以连过 A 之后换成 B：

```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@  WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!  @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
```

连不上。**这个坑虽然烦，但它是"好的失败"**：它明确告诉你出事了。

解法不是删 `known_hosts`（那样两台会永远互相覆盖），而是给每台一个名字：

```sshconfig
Host router-a
    HostName 192.168.x.x
    HostKeyAlias router-a-key

Host router-b
    HostName 192.168.x.x
    HostKeyAlias router-b-key
```

`known_hosts` 是按**你敲的名字**记的，别名不同就各存一条。之后敲错名字会直接报错——这是保护。

### 9. 连接复用：不报错，但连到了错的那台

为了省掉重复握手，我开了连接复用：

```sshconfig
Host *
    ControlMaster auto
    ControlPath ~/.ssh/cm-%h-%p
    ControlPersist 10m
```

第一条连接建好之后留着，后面的连接搭上它走——不再握手、不再输密码，快很多。

问题出在 `%h` 上：**`%h` 展开成的是 `HostName`，不是别名。**

两台路由器都是 `192.168.x.x:22`，于是**共用同一个 socket 文件**。

后果：

1. 你在 A 上挂着会话；
2. 换成 B 插上；
3. 敲命令 → 直接继承了 A 的那条通道；
4. **你以为在 B 上，其实在 A 上。**

不报错、不提示、不警告。`hostname` 当然能看出来，但谁会每次先敲一遍 `hostname`？

修法只有一个字：

```sshconfig
ControlPath ~/.ssh/cm-%n-%p     # %n = 命令行里敲的名字
```

（`%C` 也是常见写法，但它内部基于 `%h`，一样会串。）

**这是全部五个坑里最该记住的一个**：不是因为它难，是因为它**伪装得太好**。

## 四、共同的形状

这五个坑看着毫不相干，但抽出来是同一个结构：

### 1. 容错性强的格式，会把错误吞掉

Markdown 的设计目标是「纯文本也能读」，所以它对不认识的字符一律当普通文字。这带来了极强的容错，也带来了「你怎么写它都收，就是不按你想的排版」。

Git 的 `.gitignore` 同理：一个匹配不到任何东西的模式，和一条正确的规则，在行为上是完全一样的——**没有东西被忽略**。

### 2. 作用域是隐式的

「这个配置对谁生效」这件事，在 Markdown 里是「哪个渲染器」，在 Git 里是「哪一级配置」，在 SSH 里是「哪个关键字的展开时机」。

它们都**不需要你声明**，所以你也不会去想。等到出问题，你已经忘了当初写在哪一层了。

### 3. 真实状态在别处

- Markdown 的真实状态在**渲染结果**里，不在源码里；
- `.gitignore` 的真实状态在**索引**里（已跟踪的文件不受规则影响），不在规则里；
- SSH 的真实状态在**那个 socket 文件**里，不在 `~/.ssh/config` 里。

**你看到的（源码）和你以为的（结果）之间，隔着一层你没看的东西。**

## 五、怎么防

三条习惯，成本都很低。

### 1. 看结果，不看源码

写完 Markdown，一定看一眼**渲染后的样子**。GitHub、Forgejo、博客本地预览都行。

源码里"看起来对"是最不可靠的判断依据——上面那三条规则，源码里全都长得没问题。

### 2. 关键处用命令自检，不靠眼睛

下面这些我固定用，每个都是一行：

```bash
# Markdown 结构有没有丢
grep -c '^```' 文件.md           # 应该是偶数
grep -o '|' 文件.md | wc -l       # 有表格就不该是 0
grep -c '^$' 文件.md              # 空行不该是 0
grep -cP '\t' 文件.md             # 有表格就不该有 Tab

# git 忽略规则到底生效了没
git status --ignored --short

# 这次 push 到底会推什么
git push --dry-run

# 这次 clean 到底会删什么（clean 是真删，不进回收站）
git clean -nd

# 一条配置是从哪来的
git config --list --show-origin

# 有没有钩子在跑
git config --get core.hooksPath
```

### 3. 遇到"应该生效但没生效"，先问「谁的作用域」

三个方向，问完基本就定位了：

- **是谁在解析？**（Markdown 的渲染器是 GitHub、Hugo、还是编辑器预览）
- **是哪一级配置？**（system / global / local）
- **是谁状态？**（源码、索引、还是某个缓存文件）

## 最后

写代码的时候，我们习惯了「报错是好事」。编译不过、测试红了、异常堆栈指到行——这些都是**诚实的失败**，修起来最快。

真正耗时间的是**不诚实的成功**：命令退出码 0，输出干干净净，东西就是不对。

这五个坑教我的只有一件事：

> **当一段配置短得不像会出错，而且又没有任何反馈时，恰恰最该验证一遍。**

一张表格、一行 gitignore、一个 `ControlPath`，都是这种短东西。它们不报错，也不会有人提醒你。

又及：这两份速查我整理成了自己的私人笔记（Markdown 一份、Git 一份，都在 `git/` 目录下），写的时候顺手把每个坑的判断方法放进去了。这篇留的是「为什么会静默失败」和「怎么自检」，具体的语法细节在笔记里。
